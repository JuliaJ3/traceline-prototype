SHEET 01
Theme 2 · Multimodal maintenance intelligence

A citation can be real, from a real page, and still wrong.

TraceLine is a maintenance assistant whose job is not to answer faster, but to refuse to answer when it cannot do it honestly. It checks whether the evidence it retrieved actually applies to the machine in front of you — and when it cannot tell, it says which single field would settle it.

SHEET 02
The problem

The wrong-revision answer looks exactly like the right one.

A technician asks what a fault code means. Search returns a real document, with a real page number, stating a real answer — for a different firmware revision of that machine. The citation is the problem. It makes a wrong answer look verified, and someone who would have double-checked an unsourced answer does not double-check a cited one.

What a conventional assistant returns

Answered · 1 source
SRC-021 · p. 11 · table 3 7.63

On firmware 2.3.x, the table maps F12 to supply input below a configured threshold.

Troubleshooting tablefirmware 2.3.8

Real document. Real page. Correct content — for firmware 2.3.8. Confirm 2.4.1 on this asset and a different record applies. Nothing in the sentence says so.

  1. 01

    Applicability is invisible in the text

    Whether a document covers this model, firmware and supply class lives in metadata and revision tables — not in the sentence that answers the question.

  2. 02

    Documents disagree and never say so

    Two references describe the same fault code correctly, for different releases. Neither one references the other.

  3. 03

    The deciding field is often unknown

    The technician may not know the installed firmware. A system that quietly assumes a value has invented its most important input.

SHEET 03
The move

Applicability is a blocking condition, not a metadata field to display.

Most systems retrieve, rank, and answer. TraceLine inserts one step: before a record can support a statement, its declared scope must cover the confirmed asset configuration. Fail that and the record stays on screen, labelled with why it was excluded. Cannot evaluate it, and no answer is produced at all.

  1. 01

    Retrieve

    BM25 over the corpus. A query naming a fault code restricts citable records to carriers of that code.

  1. 02

    Evaluate scope

    Compare each record's declared model, firmware and supply against confirmed context. Five possible verdicts.

  1. 03

    Decide, or decline

    Scope the answer, surface the disagreement, or abstain and name the missing field. Never guess.

Four things the verdict can be, and what the interface says
VerdictBadge shownWhat it means
conflictClarification neededSources disagree and the deciding field is unconfirmed. Both cited, neither selected.
scopedContext applied · scoped answerOne record's declared scope covers the confirmed context. Others excluded with reasons.
abstainInsufficient evidenceNo record's scope matches, or nothing addresses the question. Missing evidence named.
model-scoped-abstainOut of model scopeEvidence exists, but for a different equipment platform.

SHEET 06
Multimodal input

A photo suggests. A technician decides.

Client-side OCR reads a nameplate image and writes firmware into the asset context as an ocr-sourced suggestion. The answer does not change. Only explicit confirmation promotes it to confirmed context — so machine perception informs the human and never substitutes for them.

An OCR reading is a suggestion. TraceLine will not scope an answer to a value the technician has not confirmed.

Unconfirmed is a first-class state. “No verdict available” is represented distinctly from “fails the check”. Collapsing those two is what makes a system either over-cite or silently drop valid evidence.

SHEET 08
Demonstrated, not asserted

Turn the applicability check off and the failure reproduces on demand.

The prototype ships its own control condition. One toggle removes the applicability filter, and the same F12 question — on an AX-480 asset with firmware 2.4.1 confirmed — cites four records. The top-ranked one is a troubleshooting table for the AX-320 platform.

SHEET 09
How it is built

A DOM-free rule engine, tested directly, with one runtime dependency.

score(t) = idf(t) · ( tf · (k₁ + 1) ) ─────────────────────────────── tf + k₁ · (1 − b + b · len/avglen) k₁ = 1.4 b = 0.72 idf(t) = ln( 1 + (N − n + 0.5) / (n + 0.5) )

BM25 written from scratch so the scoring is inspectable and the tests can assert on term frequencies, document lengths and the idf map directly. Scores are shown per record in the interface rather than hidden behind a relevance bar.

Applicability, evaluated in this order
#CheckVerdict when it fails
1Record model ≠ confirmed modelout-of-model
2Record supply ≠ confirmed supplyout-of-supply
3Firmware not confirmedunresolved
4Confirmed firmware outside record scopeout-of-firmware
5All checks passapplicable

Order matters. unresolved is returned before the firmware comparison, so a missing value can never be read as a failed check.

Stack
Hand-written HTML and CSS, native ES modules, no framework. Tesseract.js 5.1.0 from a CDN is the only third-party runtime dependency.
Not present
No package.json, lockfile, node_modules, bundler, transpiler, CSS preprocessor, backend, database, API key, or environment variable.
Tests
node --test · 41 tests · ~126 ms · named for the failure each one forbids. The engine imports no DOM, so the rules are tested without a browser.

SHEET 10
Honest boundaries

What is real in this build, and what is not.

A prototype that overstates itself is worth less than one that states its edges. These are the edges.

Working

In the build

BM25 retrieval with visible per-record scores · exact-identifier handling · five-verdict applicability · metadata-derived conflict detection · typed field provenance · client-side OCR with noisy-read reconstruction · documented claims separated from field observations · structured abstention that names what is missing · citation links that open the cited region · keyboard-operable evidence list, ARIA live regions, layout holding at 400 px.

Not built

Stated, not implied

No semantic embeddings or vector store — retrieval is lexical only. No PDF parsing, no real table or diagram extraction, no LLM generation, no backend, no authentication, no persistence. The diagram regions are human-authored fixtures, not computer-vision output. No accuracy has been measured; the idea-phase targets are hypotheses to test, not results.

Every equipment identifier, document title, excerpt, date and revision is synthetic. Nothing is reproduced from manufacturer documentation, and no integration or endorsement is claimed. TraceLine does not control equipment, diagnose physical faults, or authorise work — the interface says so on every screen.

SHEET 11
Why it scales

The rules are pure functions over record metadata.

Nothing in the approach is specific to drives or firmware. The same rules hold when the corpus becomes an ingestion pipeline instead of a fixture array, and they apply to any domain where evidence is scoped — model, serial range, supply class, region, effective date — and where citing out-of-scope evidence is worse than citing nothing.

01Replace the fixture corpus with ingested records carrying the same declared-scope fields. The verdict logic does not change.
02Every exclusion is derived from declared metadata, so it is auditable after the fact — the minimum bar for regulated maintenance work.
03Next step: run the workflow against approved documents, with engineers reviewing the applicability labels.
